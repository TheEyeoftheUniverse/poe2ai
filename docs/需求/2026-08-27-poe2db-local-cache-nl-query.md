# poe2ai 一期需求：poe2db.tw 全站快照 + 自然语言查询

> 范围: poe2ai 插件一期——poe2db.tw 的**全站数据**（装备、词条、技能、怪物、路石/地图、任务、制作机制等全部类别）以「仓库自带快照」为主、按需拉取兜底，用户用自然语言提问时，由 LLM 主动调用工具查本地数据作答。
> 目标:「让 AstrBot 帮我翻 wiki」。用户（仓库主人本人）就是最终用户。
> **用户约束（原话）:「我自己翻这个wiki是很费神的」——交互形态必须是自然语言直问直答，而不是让用户再学一套手动查询指令。**
> 数据源: https://poe2db.tw/（Path of Exile 2 社区数据库 wiki）

## 背景

用户玩 Path of Exile 2，日常需要查 poe2db.tw（装备基础数据、词条池等）。该站信息量大、页面密，人工翻阅费神。poe2ai 作为 AstrBot 插件，要把「翻 wiki」这件事交给聊天机器人：用户在聊天里随口问，机器人查数据、给答案。

## 需求清单（FR-0～FR-5 已定稿）

| # | 需求 | 来源（用户原话） |
|---|---|---|
| FR-0 | **全站快照**:poe2db.tw **全部类别**的结构化数据打包进本仓库，随插件分发，装好即用、零冷启动 | 决议 Q1 + 2026-08-27 全站修订（用户原话:「要全站抓。」） |
| FR-1 | **本地优先**：查询默认只读本地数据，不请求网站 | 「最好是能把内容都存在本地」「不要让它每次都去翻」 |
| FR-2 | **按需拉取兜底**：快照里查不到时才去 poe2db.tw 拉对应整页、解析入库，下次直接命中 | 「本地没有的才去这个网站里面更新数据」 |
| FR-3 | **装备查询（带图）**：按名称查装备（基础属性、需求、效果等），回答时装备信息与图片（icon_url 外链）一起发送 | 「在我询问某个装备……的时候帮我翻阅存储在本地的wiki内容」+决议 Q5「它就可以找到这个装备，连着装备的信息和图片一起发给我」 |
| FR-4 | **词条查询**：按词条（affix/mod）查数值区间、出现部位/物品类型等 | 「……或词条的时候」 |
| FR-5 | **自然语言主动调用**：注册为 LLM 工具（function calling），用户自然语言提问时模型自主决定调用并直接作答 | 「直接在我用自然语言问他的时候，它会主动调用工具去翻本地wiki，然后就能回答我」 |

范围注:全站快照下，技能宝石、怪物、路石/地图、精华、任务等类别的查询能力随快照自然获得，工具注册与查询模式与装备/词条同构（一期验收以装备+词条为准，其余类别作为快照数据先行入库）。

### FR-5 补充说明（交互形态关键）

- 触发方式是 **LLM 自主调用**（AstrBot 的 `llm_tool` 机制），不是 `/指令` 触发。用户问「t1 攻速是多少」这类问题时机器人自己查、自己答。
- 手动指令不是用户主路径，仅作运维口（见决议 Q2 的刷新指令）。

## 非功能约束

- NFR-1 **省人**：本插件存在的理由。回答要直接、结论化（数值区间、部位、结论），不要丢链接让用户自己看（装备图除外——图随信息一起发，不是替代信息）。
- NFR-2 **礼貌抓取**：poe2db.tw 是免费社区站、无官方 API。全站构建为一次性离线任务，**必须限频**（建议 1 请求/秒级），整轮跑几十分钟属正常;运行期按需拉取同样限频;不做重复全站爬取。
- NFR-3 **快照体积**：全站结构化文本预估十几~几十 MB（精确值以首次构建实测为准，上限约束 100MB），**不打包任何图片文件**（图片以 icon_url 外链形式存于数据记录中）。

## 收紧决议（2026-08-27 拍板，AskUserQuestion + 追加确认）

1. **Q1 数据范围 → 插件自带快照 + 按需兜底（用户提议），同日修订为全站**。用户反问「能不能自带数据」，实测验证可行：
   - 全部词条:`/cn/Modifiers` 总页一页 450KB HTML 即覆盖（含数值区间、分组）。
   - 装备类型页约 25~35 张:普通装备页 37~89KB/张（Helmets/Belts/Jewels/Crossbows 实测），含大量 unique 物品的页可达 0.6~2.7MB/张（Rings/Bows/Amulets 实测，HTML 标签与重复导航占了大部分）。
   - 结论:剔除 HTML 冗余、词条与装备页内词条去重后，**装备基底+全部词条结构化数据预估 1~3MB 文本**，打进仓库毫无压力。
   - 运行形态 = FR-0 快照为主 + FR-2 按需拉取兜底（快照落后或查到快照外数据时）。
   - **修订（2026-08-27，用户原话:「要全站抓。」）**:快照范围从装备+词条扩大为**全站全部类别**——技能宝石（几百页）、天赋树、怪物数据库（估计几千页）、路石/地图、任务、精华、催化剂、制作机制等。全站页面估计几千~万余页（无 sitemap 实测 404，按类别索引页枚举），纯文本结构化后预估十几~几十 MB，仓库可承受。全站抓为一性次离线构建（限频慢跑），一期查询工具验收仍以装备+词条为主，其余类别数据先行入库、查询工具随后同构扩展。
2. **Q2 数据时效 → 不过期 + 手动刷新指令**。默认永信本地；留一条运维指令（如 `/poe2 刷新`）手动重拉指定页/全量，大版本更新后用户自己敲。
3. **Q3 语言 → 中文版为主 + 中英别名兼容**。快照抓 `/cn/` 中文站、中文作答；查询层做中英别名（如「t1 攻速」能命中英文词条名），不做双语双缓存。
4. **Q4 抓取粒度 → 整页拉**。按需兜底时拉取该词条所属的整张「物品类型页」解析入库，之后同页全部词条本地命中；单条词条无独立干净入口，不做精确单条。
5. **Q5 图片 → 不打包图片文件，存 icon_url 外链（用户拍板）**。实测依据:词条行内小图标仅 1.5KB/张且全局复用（全套 <1MB，无必要）；装备/unique 物品图打包会达 20-60MB，且 git 历史对二进制只增不减;`cdn.poe2db.tw` 公开可访问、支持外链。**使用场景（用户原话）:「我问ai某某装备是什么效果，它就可以找到这个装备，连着装备的信息和图片一起发给我」**——数据记录存 icon_url 字段，回答装备问题时信息+图一起发，图片走外链，本地零图片存储。全站各类别数据记录同样只存 icon_url，不下载图片。

## 技术备注（方向参考，非决议）

- poe2db.tw 为纯静态站、服务端渲染表格，数据直接在 HTML 中；`/export` 端点实测 404、`/sitemap.xml` 实测 404，**无现成 JSON API 与站点地图**，全站页面清单需从各分类索引页（`/cn/` 导航 + Items/Modifiers/EndGame 等）递归枚举。
- 图片 CDN:`cdn.poe2db.tw`，webp 为主，外链可用。
- 快照格式倾向 SQLite（词条区间查询友好）或 JSON 文件；构建脚本放仓库内（`tools/`），可重复执行以更新快照（限频全量重跑）。
- AstrBot 侧用 `@filter.llm_tool` 注册工具，供宿主 LLM 在对话中自主调用；发图用消息组件引用外链 URL（`image_result` 一类机制），不下载图片。
